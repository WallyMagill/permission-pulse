# Codex handoff — Permission Pulse demo video

Paste everything below the line into a Codex session started at the repo
root, after v0.7.2 has passed its human gates (the app must launch and

---

You are planning and assisting a screen-recorded demo video of
**Permission Pulse**, a free open-source macOS menu-bar app for
permission hygiene, at `github.com/WallyMagill/permission-pulse`. The
human operator records on their own Mac; you produce the plan and drive
the checklist. Read these files completely before anything else:
`README.md`, `docs/09-roadmap.md`, `scripts/seed-diff.sh`.

## Objective

A ~60–90 second demo video for the GitHub README and release
announcement: tight, real, no filler. Deliver a storyboard, an exact
click path, a narration script, and a recording-setup checklist the
operator can follow top to bottom.

## Locked decisions — do not relitigate

1. Feature order: menu-bar live mic/cam indicator → dropdown status
   rows → Overview → Permission Inbox with the risk inspector open →
   What Changed (seed a diff first with `scripts/seed-diff.sh`, then
   Refresh) → Stale Apps review → one-click System Settings deep link.
2. Real data only. Nothing fabricated on screen; if the operator's Mac
   lacks a state (e.g. no stale apps), the scene is cut, not faked.
   Warn the operator that scan results expose their installed apps —
   they choose a recording account accordingly.
3. Visual identity is the app's brand blue; record in whichever
   appearance (light/dark) the storyboard argues is stronger, but pick
   one and say why.
4. Narration ≤ 220 words total, plain language, no feature-list drone.
   Written to be read aloud by the operator (or used as captions).

## Verification gates

- Before scene planning: confirm the app launches and the seeded diff
  actually renders a row in What Changed (operator runs
  `scripts/seed-diff.sh`, clicks Refresh, reports what they see).
- Storyboard timings must sum to ≤ 90 seconds with per-scene durations.
- Every scene names the exact UI element clicked, so the operator never
  improvises mid-take.

## Stop boundary

Read-only session. No file edits, no commits, no `git` state changes,
no `sudo`, nothing published or uploaded anywhere. The recording, any
editing, and any upload are the operator's manual steps.

## Response contract

Reply with a single markdown document containing, in order:
(1) recording setup — display resolution, cursor size, screen-recording
tool and settings, menu-bar cleanup, do-not-disturb;
(2) pre-flight data seeding steps with the exact commands;
(3) the storyboard table — scene, duration, on-screen action, narration
line;
(4) the full narration script as one block;
(5) a post-recording checklist — trim points, export settings, target
file size, and where to put the file (`docs/` is NOT the place for a
video; recommend attaching to the GitHub release or linking).
